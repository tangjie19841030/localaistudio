# 本地 AI UI Studio 开发方案

## 1. 项目定位

开发一个仅供个人使用、默认离线运行的 AI UI 设计与代码生成工具。它不是完整复刻 Figma，而是一个本地版的 "Figma Make Lite"：用户提供文字需求、参考截图和品牌规则，工具生成可编辑的网页 UI，并导出可维护的 React 代码。

项目名称暂定为 **Local AI UI Studio**。

核心目标：

- 不依赖按次计费的云端 AI API；默认使用本机 Ollama 模型。
- 生成真实的 React、TypeScript、Tailwind 和 shadcn/ui 代码，而不是只输出图片。
- 在可视化预览中点选组件，局部修改布局、样式与文案。
- 通过多尺寸截图发现排版问题，并让 AI 在明确范围内修复。
- 项目数据、参考图和生成代码默认保存在本机。

## 2. 产品边界

### 2.1 第一版要解决的问题

1. 从一句产品描述和一张或多张参考图，生成一页可运行的 Web UI。
2. 将页面拆成可复用的语义组件，例如导航、统计卡片、数据表、表单和设置面板。
3. 用户在预览中选中元素，修改 token 或给出局部自然语言指令。
4. 输出一个可独立运行的 React 项目代码包。
5. 以桌面、平板、手机三种视口自动截图，检查布局、溢出与可读性。

### 2.2 第一版明确不做

- 不兼容 `.fig` 文件，也不尝试导入完整 Figma 文档。
- 不实现完整矢量编辑、钢笔工具、布尔运算、复杂原型连线或多人评论。
- 不实现实时多人协作、组织权限、在线发布和计费。
- 不直接把 AI 输出的任意代码写入本机其他目录或执行任意 shell 命令。
- 不承诺生成的业务逻辑、无障碍或安全实现可以不经人工审查直接上线。

这些限制是刻意的。个人工具的价值在于更快地得到高质量、可运行的页面，不在于复制一整套设计协作平台。

## 3. 目标用户与典型流程

目标用户是有基础开发能力、希望快速探索 UI 方向的个人开发者或产品设计者。

典型流程：

1. 新建项目，填写产品类型、目标用户、页面目标和可选参考链接。
2. 上传参考截图，填写品牌色、字体偏好和不希望出现的设计风格。
3. 选择一个本地模型，生成页面计划和第一版 UI。
4. 在预览中单击某个元素，例如筛选栏或数据卡片。
5. 输入“把这里改得更紧凑，适合每天高频操作；不要动其他区域”。
6. 工具显示变更计划和文件 diff，用户确认后应用。
7. 执行多视口截图检查；针对溢出、文字截断或层级问题继续迭代。
8. 导出 React 项目或复制单个组件。

## 4. 产品体验

第一版采用三栏工作台，不先构建无限画布。

```text
+----------------+---------------------------+----------------------+
| 需求 / 参考图  | 可交互的真实页面预览       | 属性 / Token / 图层    |
| AI 对话与历史  | 点击选择、缩放、视口切换   | 局部样式与组件配置     |
+----------------+---------------------------+----------------------+
| 代码 Diff | 运行日志 | 截图检查 | 版本历史                         |
+-----------------------------------------------------------------+
```

中间区域渲染的是真实 DOM 页面，而非在 Canvas 上画出的“假网页”。这有三个直接收益：

- 页面行为、响应式规则和文本换行与导出的代码一致。
- 可以利用浏览器原生检查、键盘导航和 Playwright 截图。
- 用户点选的是语义组件，不是没有业务含义的矩形图层。

需要自由排版时，使用有限的拖拽能力：调整区块顺序、栅格列数、组件尺寸和对齐方式。不要让用户在 MVP 中随意拖出不可维护的绝对定位页面。

## 5. 总体架构

```text
React 工作台
  |-- 项目管理、设计面板、预览、Diff、版本历史
  |-- IndexedDB：项目元数据、Schema、Token、聊天记录
  |
本地 Node 服务
  |-- Ollama 代理：模型选择、流式输出、取消任务
  |-- 代码工作区：只允许写入应用专属 projects/ 目录
  |-- Vite 预览进程：隔离运行每个生成项目
  |-- Playwright：多视口截图和基础验收
  |
Ollama
  |-- 编程模型：负责规划、生成、修复 TypeScript/React 代码
  `-- 可选视觉模型：理解用户上传的参考图和截图反馈
```

第一版做成本地 Web 应用：前端和 Node 服务只监听 `localhost`。这样开发、调试和插件接入最简单。稳定后可以用 Tauri 将其打包为 Windows 桌面应用，保留同一套 React 界面与本地服务能力。

## 6. 技术选型

| 层级 | 选型 | 原因 |
| --- | --- | --- |
| 前端工作台 | Vite、React、TypeScript | 本地启动快，组件生态成熟。 |
| UI 基础 | Tailwind CSS、shadcn/ui、Lucide | 生成代码可读、可复制，避免自建低层组件。 |
| 状态管理 | Zustand | 适合编辑器的局部状态、撤销栈和面板状态。 |
| 持久化 | IndexedDB + Dexie | 个人离线项目不需要先建数据库。 |
| 拖拽/排序 | dnd-kit | 只做区块排序和布局调整，避免过早做图形编辑器。 |
| 代码查看 | Monaco Editor | 用于只读代码、Diff 和少量高级手改。 |
| 本地 AI | Ollama + 可配置的本地编程模型 | 运行不产生 API 调用费，模型可替换。 |
| 本地服务 | Node.js + Hono | 处理文件、模型代理、预览进程和截图任务。 |
| 预览 | 独立 Vite dev server + iframe | 让生成项目运行在隔离预览地址中。 |
| 视觉验收 | Playwright | 按固定视口截图、检查控制台错误和基本交互。 |
| 打包（后续） | Tauri | 比 Electron 更轻，适合纯本地个人工具。 |

如果以后确实要加入自由画布，可评估 `react-konva`。但它不应阻塞第一版，因为高质量的网页导出主要依赖结构化布局和真实 DOM。

## 7. 关键设计：页面 Schema 优先

AI 不能只生成一份不可控的大 JSX 文件。系统需要先维护一个受约束的页面 Schema，再从 Schema 渲染预览和生成代码。

示例：

```json
{
  "documentVersion": 1,
  "name": "运营工作台",
  "tokens": {
    "color": {
      "brand": "#0F766E",
      "surface": "#FFFFFF",
      "text": "#172033"
    },
    "radius": { "card": 6, "control": 4 },
    "spacing": { "unit": 4 }
  },
  "nodes": [
    {
      "id": "app-shell",
      "type": "AppShell",
      "props": { "sidebar": true },
      "children": ["overview-header", "metrics-grid", "recent-table"]
    },
    {
      "id": "metrics-grid",
      "type": "MetricGrid",
      "props": { "columns": { "desktop": 4, "mobile": 1 } }
    }
  ]
}
```

Schema 的约束：

- 只能使用注册过的组件和属性，禁止 AI 捏造不存在的组件接口。
- 布局优先使用 Stack、Grid、Container 和语义区块，绝对定位只可用于明确标记的装饰元素。
- token 与组件属性分离；改品牌色不应该产生大量硬编码颜色修改。
- 每个节点有稳定 ID，方便点选、局部改动、历史追踪和测试定位。
- 生成的 TypeScript 文件可重新同步到 Schema；同步失败时显示冲突，不静默覆盖人工改动。

## 8. AI 工作流

### 8.1 输入上下文

每次生成或修改使用以下上下文，而不是只传一句模糊提示：

- 页面目标、用户角色和主要任务。
- 当前页面 Schema、组件目录和 token。
- 用户上传的参考图，以及可选的视觉模型摘要。
- 当前代码、最近截图和已有问题列表。
- 明确修改范围，例如 `metrics-grid`，以及“不可修改”的节点列表。

### 8.2 两阶段生成

1. **先规划**：模型返回页面结构、需要的组件、信息层级、响应式策略和风险说明。
2. **后执行**：模型按照受限 JSON 或统一 patch 格式提出 Schema/代码变更。系统校验通过后，再交给用户确认。

每次 AI 改动都必须包含：改动目的、涉及节点、影响文件和回退点。不要让模型静默重写整页。

### 8.3 局部编辑

用户在预览中选中元素后，编辑请求将携带节点 ID 和组件上下文。例如：

```text
目标：recent-table
请求：压缩表格行高，突出异常数据；保持列结构和现有文案。
约束：只可修改 recent-table 和直接关联的 token。
```

系统先产出变更计划，确认后生成 patch。任何超出节点范围的修改都应被拦截并要求重新确认。

### 8.4 模型策略

- 默认：本地编程模型，擅长 TypeScript、React、CSS 和结构化输出。
- 有参考图时：可选接入本地视觉模型，先将图片转成视觉摘要，再交给编程模型实现。
- 模型失败或输出格式错误时：保留原版本，显示原始响应并允许重试。
- 模型名称、上下文长度和温度写入项目设置，确保结果可复现。

本地模型有硬件与速度取舍。内存较小的电脑可选择较小模型完成局部修改；更大的模型或独立显卡更适合整页生成和参考图分析。模型占用的磁盘空间和电力仍是实际成本。

## 9. 代码生成与预览

每个项目使用以下受控目录结构：

```text
projects/<project-id>/
  design/document.json
  src/components/generated/
  src/components/custom/
  src/pages/
  src/styles/tokens.css
  tests/visual/
  snapshots/
```

生成策略：

- `generated/` 仅由 Schema 代码生成器管理。
- `custom/` 用于用户或 AI 写的业务扩展，不被重新生成器覆盖。
- token 统一写入 CSS variables 和 Tailwind theme 映射。
- 导出前运行 TypeScript 检查、ESLint 和构建。
- 预览使用 iframe 隔离，工作台页面不直接执行生成项目的脚本。

## 10. 视觉验收闭环

AI UI 的质量控制不应该依赖“看起来不错”的主观描述。每次生成后自动执行：

1. 构建和启动预览。
2. 以 `1440x900`、`1024x768`、`390x844` 三个视口截图。
3. 收集 JavaScript 控制台错误、网络失败和页面溢出信息。
4. 检查可见文本是否截断、交互元素是否重叠、横向滚动是否异常。
5. 将截图与问题清单回传给 AI，限制其修复范围。
6. 生成新的版本，保留前一版本供比对与恢复。

第一版不做像素级“与参考图一致”的评分。更可靠的起点是结构检查、溢出检查和用户可见的前后截图比较。

## 11. 开发阶段

### P0：工程骨架

- 初始化 Vite React TypeScript 项目。
- 建立本地 Hono 服务与 `/api/health`、`/api/projects` 接口。
- 建立项目目录、Schema 类型、token 类型和版本存储。
- 搭建三栏工作台静态界面。

验收：可创建、保存、打开一个离线项目；重启后数据仍存在。

### P1：无 AI 的可编辑页面

- 实现组件注册表与 JSON Schema 渲染器。
- 支持 AppShell、Header、Section、Grid、Card、Button、Form、Table 等基础组件。
- 支持层级树、节点选中、属性面板和 token 编辑。
- 支持撤销、重做、版本命名和 JSON 导入/导出。

验收：用户无需 AI，也能拼出并保存一个响应式后台页面。

### P2：本地 AI 生成与局部修改

- 接入 Ollama 代理、模型检测和流式响应。
- 实现“规划 -> 校验 -> 确认 -> patch”链路。
- 支持由产品描述生成 Schema，支持选中节点后的局部修改。
- 实现变更预览和一键回退。

验收：本地模型可从一段需求生成单页，并可以只修改选中的卡片或表格。

### P3：真实代码与预览

- 实现 Schema 到 React/Tailwind 的代码生成器。
- 在隔离 iframe 中启动生成项目。
- 接入 Monaco 查看代码和 Diff。
- 实现导出完整项目 zip 或目标文件夹。

验收：导出项目可在独立环境中安装依赖、启动和构建成功。

### P4：视觉检查与产品化

- 接入 Playwright 多视口截图。
- 展示截图、问题清单和版本对比。
- 增加模板库、常用 token 预设和导入参考图。
- 用 Tauri 打包为 Windows 本地应用。

验收：从需求到导出页面的完整流程可离线完成，且每次发布前能查看三种视口截图。

## 12. 测试策略

| 类别 | 重点 |
| --- | --- |
| 单元测试 | Schema 校验、节点 patch、token 解析、代码生成器。 |
| 组件测试 | 选中、属性修改、撤销/重做、拖拽排序。 |
| 集成测试 | Ollama 流式响应、AI 输出格式失败、版本回滚。 |
| E2E 测试 | 新建项目、生成页面、局部修改、导出代码。 |
| 视觉测试 | 三个固定视口的截图、溢出与控制台错误检查。 |
| 手工测试 | 本地模型无响应、磁盘不足、用户手改代码后的同步冲突。 |

## 13. 安全与数据原则

- 默认不上传项目、截图、提示词和生成代码到第三方服务。
- 本地服务仅监听 `localhost`，不提供公网访问入口。
- 只允许 AI 修改项目专属目录；禁止访问用户的其他文件夹。
- 模型的文件写入必须经 Schema 校验或用户确认，不允许模型自行执行命令。
- 启用外部云模型、外部图片分析或在线部署时，必须在设置中显式开启并展示将发送的数据范围。

## 14. 后续可选能力

这些能力放在 MVP 稳定后评估：

- 从网页截图提取组件层级和设计 token。
- 对接本地 Git 仓库，生成分支与 commit。
- 生成页面流程和点击原型。
- 读取已有 React 项目，反向生成可视化 Schema。
- 引入实时协作；需要时可基于 Yjs 处理共享文档和冲突合并。
- 自定义组件市场和项目级 AI 规则文件。

## 15. 成功标准

第一版成功不以“像 Figma”衡量，而以以下结果衡量：

- 用户可以在不写初始代码的情况下完成一页可运行的 Web UI。
- 用户可以通过点选和自然语言指令稳定地修改局部区域。
- 输出的代码结构清晰，能独立构建，不依赖本工具运行。
- 三个目标视口没有明显文字截断、横向溢出或控件重叠。
- 全流程在本机可完成，除模型下载外没有强制云端依赖或 API 调用费。
